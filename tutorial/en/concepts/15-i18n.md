# 15 — Internationalisation

> **Time:** about 2–3 hours · half of it translating

## Goal

The app speaks German and English, switchable through a menu — and adding a third language is
**one file and nothing else**. No import, no entry in a list, no code change.

This is an extension chapter: the app is finished after [Build and
deployment](14-build-deployment.md). Here a capability gets added that in real projects is almost
always retrofitted rather than planned for — with everything that means in terms of tidying up.

---

## First the question: library or build it yourself?

For internationalisation the first thought is something simple: a file with keys, a function
that looks them up. Sixty lines, done. The project has no dependency it doesn't need, after
all.

Until you hit **plurals**.

In this project the subject list of an academy had this:

```ts
// This is what was really in the code
`${academy.subjectLabel}e`
```

Append an "e", done. For the Jedi that gave "Lehrpfade", for the Rebels "Kurse" — looks fine.
And for the other two:

```
sith    'Lehre'           + 'e'  ->  'Lehree'            ✗
empire  'Ausbildungsfach' + 'e'  ->  'Ausbildungsfache'  ✗
```

**Two out of four were broken, in a single language.** That isn't carelessness, it's the nature
of the thing: German plurals use `-e`, `-en`, `-er`, `-¨er`, a zero plural and exceptions.
English has `-s`, `-es`, `-ies` and irregulars. Polish has three plural forms depending on the
number. Arabic has six.

Which is why this chapter uses a library — **vue-i18n**:

```jsonc
"subjectLabel": "Lehre | Lehren"
```

```ts
t('academies.sith.subjectLabel', 6)   // "Lehren"
t('academies.sith.subjectLabel', 1)   // "Lehre"
```

Which form applies at which count is the library's job, per language.

> **The transferable lesson.** "Build it yourself" is a good default — until you hit a domain
> where special cases have been collected for decades. Language, time zones, calendars,
> character encoding, cryptography: there the library wins, and not narrowly. The art is
> recognising the difference before the bug is in production.

## Finding locale files instead of listing them

This is the central design decision. The obvious approach would be:

```ts
// NOT like this
import de from './locales/de.json'
import en from './locales/en.json'
const messages = { de, en }
```

That works — and is exactly the place you forget when adding a language. Vite can find files
itself:

```ts
const modules = import.meta.glob<{ default: LocaleFile }>('./locales/*.json', { eager: true })

const messages = Object.fromEntries(
  Object.entries(modules).map(([path, module]) => [localeFromPath(path), module.default]),
)
```

`import.meta.glob` is a **Vite function**, not a JavaScript standard. It resolves the pattern at
build time and generates the imports itself. `eager: true` means the files go straight into the
bundle instead of being loaded on demand — with a handful of small JSON files that's the
simpler choice.

### The display name belongs in the file

The menu needs readable names: "Deutsch", not "de". From where?

```jsonc
{
  "_name": "Deutsch",
  "app": { … }
}
```

From the file itself. If the mapping `{ de: 'Deutsch', en: 'English' }` lived in the code, you'd
have a second list to maintain — and with it exactly the problem the glob just solved.

```ts
export const AVAILABLE_LOCALES = Object.entries(messages)
  .map(([code, message]) => ({ code, name: message._name }))
  .sort((a, b) => a.name.localeCompare(b.name))
```

**The rule behind it:** if adding something has to be maintained in *two* places, one of them
will eventually be forgotten. Derive the second from the first.

## The test that makes good on the promise

"Adding a language is just one file" — nicely put. But what happens when someone creates
`wookiee.json` and forgets three keys?

Without a safety net: somewhere in the interface `login.password` appears instead of a text.
Maybe it gets noticed, maybe only weeks later on a screen few people open.

Hence this test:

```ts
it.each(locales.filter((code) => code !== DEFAULT_LOCALE))(
  'has the same keys in "%s" as in the default language',
  (code) => {
    const expected = new Set(flatKeys(messages[DEFAULT_LOCALE]))
    const actual = new Set(flatKeys(messages[code]))

    const missing = [...expected].filter((key) => !actual.has(key)).sort()
    const extra = [...actual].filter((key) => !expected.has(key)).sort()

    expect({ missing, extra }).toEqual({ missing: [], extra: [] })
  },
)
```

`flatKeys` turns the nested object into a flat list of paths (`login.password`,
`academies.sith.motto`, …). The comparison then reports not just "something is missing" but
**exactly what**:

```
- "missing": [],
+ "missing": [
+   "academies.sith.motto",
+   "login.password",
+   "nav.signOut",
+ ],
```

This is the actual heart of the chapter. Not the library, not the glob — **this test** is what
turns "extensible in theory" into a promise you can rely on.

`extra` matters just as much: it catches typos in key names. Write `login.passwort` and you see
one missing *and* one extra key.

> **Try it.** Copy your `de.json` to `klingon.json`, delete three keys, run the test. That
> feeling — the test telling you what you forgot — is what you want in every project that's
> meant to be extensible.

## What gets translated and what doesn't

The harder half isn't the technology, it's deciding **which string is language and which is
data**.

| | Example | Translate? |
| --- | --- | --- |
| Interface text | "Sign in", "Save" | **Yes**, obviously |
| Role and subject labels | "Padawan", "Course" | **Yes** — they're labels, not names |
| Subject names | "Exerzierdienst" → "Drill Duty" | **Yes** — descriptive titles |
| Grade labels | "In balance" | **Yes** |
| People's names | "Ahsoka Tano" | **No** — proper nouns |
| Codes | `EXD`, `TIE` | **No** — identifiers like module numbers |
| IDs and logins | `f13`, `yoda` | **No** — technical identifiers |

The borderline case is the **codes**. "EXD" stands for "Exerzierdienst" — in English it should
be "DRL". But: at a real university a module number is an identifier that stays stable for
years and appears on transcripts. Which is exactly why it stays here.

**What follows from that is a rebuild of the master data.** `data/academies.ts` previously held
everything — name, motto, labels, grade labels. Now it holds:

```ts
export const ACADEMIES = [
  { id: 'jedi' },
  { id: 'sith' },
  { id: 'empire' },
  { id: 'rebels' },
] as const satisfies readonly Academy[]
```

Structure only. And `Person.roleLabel` has disappeared entirely: the label follows from role
plus academy and lives in the locale files.

> **The principle from [Domain model](06-domain-model.md) still holds, just more precisely.**
> Back then it said: everything language-shaped belongs in one place and is not derived from
> the name. That place was the academy file, now it's the locale files. And nothing is derived
> from the name, exactly as before.

## Access from the views

Without help every view would carry an assembled key chain:

```vue
{{ t(`academies.${academy.id}.studentLabel`, 2) }}
```

Error-prone and hard to find when renaming. A composable bundles it:

```ts
export function useAcademyLabels(academyId: MaybeRefOrGetter<AcademyId | null | undefined>) {
  const { t } = useI18n()
  const base = computed(() => { … })

  return {
    name: computed(() => key('name')),
    lecturerLabel: computed(() => key('lecturerLabel')),
    studentLabel: (count: number) => t(`${base.value}.studentLabel`, count),
    subjectLabel: (count: number) => t(`${base.value}.subjectLabel`, count),
    gradeLabels: computed<Record<Grade, string>>(() => …),
  }
}
```

Note the difference: `name` is a `computed`, `studentLabel` is a **function**. The reason is the
plural — only the caller knows the count.

```vue
<StatTile :label="labels.subjectLabel(ownSubjects.length)" :value="…" />
<th>{{ labels.subjectLabel(1) }}</th>
```

### Pure functions stay language-free

`accessEntriesFor()` in `data/seed.ts` used to build finished display strings:

```ts
display: person.role === 'lecturer' ? `${fullName(person)} (${person.roleLabel})` : fullName(person)
```

That no longer works — the bracket depends on the language, and a pure function shouldn't be
handed a translator. So it returns **raw data** and the view composes:

```vue
{{ entry.isLecturer ? `${entry.name} (${labels.lecturerLabel.value})` : entry.name }}
```

The gain shows up in the test: `accessEntriesFor` stays checkable without a translator, without
a component and without a store.

## Two details people overlook

### `<html lang>` is not a detail

```ts
document.documentElement.lang = stored.value
```

Screen readers pick their **pronunciation** from it. Without switching it, a German voice reads
the English text aloud — comprehensible it is not. The page title in the browser tab takes the
same route; otherwise it stays permanently in whatever language `index.html` was written in.

### Quotation marks depend on the language

German writes „so", English "so", French « so ». If you type the characters into the template,
they're wrong in one of the languages:

```vue
<!-- wrong as soon as there's more than one language -->
<p>„{{ motto }}"</p>

<!-- right: the browser picks them from <html lang> -->
<q>{{ motto }}</q>
```

That's exactly what `<q>` is for. An element most people never use — and one that has a real
job here.

## Your task

1. `npm install vue-i18n`, then `src/i18n/index.ts` with `import.meta.glob`, `fallbackLocale`
   and the derived `AVAILABLE_LOCALES`.
2. Create `src/i18n/locales/de.json` (or `en.json` — pick your source language) and move
   **all** interface text there.
3. **Write the completeness test first**, before the second language exists. Then it tells you
   what's still missing while you translate, instead of you checking afterwards.
4. Reduce `academies.ts` to the IDs, remove `Person.roleLabel`, move the subject names.
5. Write `useAcademyLabels`, convert the views, fix the plurals.
6. `useLocale` with persistence via `useLocalStorage`, the browser language as the starting
   value, `<html lang>` and the page title.
7. `LanguageSelect` in the navigation — it's visible **before** sign-in too, and without a
   language picker on the sign-in screen the best translation helps nobody.
8. Translate the second locale file.
9. Cross-check: create a third locale file with deliberate gaps, run the test, delete the file
   again.

## Pitfalls

| Symptom | Cause |
| --- | --- |
| A raw key in the interface (`login.title`) | key missing or mistyped — exactly what the completeness test catches |
| The plural is wrong in one language | the `\|` form is missing in the locale file, or `t(key)` was called without a count |
| Component tests throw on mount | i18n plugin missing — provide it globally in the test setup, not in every test |
| The language choice is gone after a reload | persistence forgotten |
| Screen reader reads it wrong | `<html lang>` not kept in sync |
| Type error in `createI18n` | vue-i18n infers a fixed schema from the first locale file; with glob-discovered files you have to loosen the type |
